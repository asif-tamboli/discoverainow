Original benchmark framework

The DiscoverAINow AI Testing Benchmark.

A transparent way to compare AI models on the work software testers actually do—not on generic chatbot demos.

Methodology v1 · Results are not published until experiments are actually run
Status: methodology published, benchmark runs pending.We are intentionally publishing the scoring framework before publishing scores. That prevents us from changing the rules after seeing which model performs best.

Six benchmark tasks

  1. Requirement interpretation: identify ambiguity, dependencies and missing acceptance criteria.
  2. Test-case generation: produce positive, negative, boundary and state-transition coverage.
  3. Edge-case discovery: identify meaningful non-obvious failures rather than producing long generic lists.
  4. API testing: generate useful test scenarios and validations from an API contract.
  5. Automation generation: create maintainable Selenium/Playwright-style test code from a defined scenario.
  6. Defect analysis: reason from symptoms/logs to reproducible hypotheses without inventing evidence.

100-point scoring rubric

DimensionWeightWhat earns points
Correctness25Technically and logically correct output; no invented requirements.
Coverage20Important positive, negative, boundary and dependency cases.
Risk prioritization15Finds high-impact risks instead of treating every case equally.
Automation quality15Readable, maintainable and appropriately synchronized code.
Hallucination control15Flags uncertainty instead of inventing facts or interfaces.
Manual cleanup10How close the output is to something a practitioner can use.

Representative benchmark requirement

Feature: Card payment limit A customer can make a card purchase when: - the card is active; - the transaction is below the remaining daily limit; - sufficient available credit exists. The daily purchase limit resets at midnight in the account timezone. Declined transactions must not reduce available credit or the daily limit.

The same source requirement is supplied to every model. Scorers then compare whether the output catches boundary behavior, timezone reset, concurrent transactions, exact-limit behavior, decline-state integrity and missing/ambiguous requirements.

Why this is useful

Benchmarking makes comparison pages auditable. Instead of saying one model “feels better,” we can show which cases it found, which it missed and how much human correction was required.
